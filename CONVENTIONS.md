# LinuxServer v2 conventions

This file is the contract every repository in the `linuxserver-playground` organisation is built
against. The JSON Schemas in `schemas/` are the machine-checkable half; this document is the half that
explains intent. When a repo's own docs and this file disagree, this file wins. Change it by pull
request to this repo, and bump `contracts_version` in `pyproject.toml` when a schema changes shape.

The blueprint behind these conventions is the "LinuxServer v2 Blueprint" page. The short version:
image repos are thin and described by one manifest; one shared GitHub Actions workflow builds every
image; each build attaches a bundle to its GitHub Release; the hub ingests bundles and generates every
downstream artefact; a public control plane schedules builds and shows the whole fleet.

## 1. Repositories

| Repo | Owns | Hand-edited files |
| --- | --- | --- |
| `builder` | Contracts (this file, `schemas/`), the manifest validator and renderer, AGENTS.md templates | everything |
| `workflows` | Reusable GitHub Actions workflows and composite actions, tagged `v1` | everything |
| `ci` | The container test harness and bundle emitters | everything |
| `hub` | Ingest, data, static API, generators (docs pages, stores, proxy confs, kubernetes, mods index) | everything except `data/` |
| `control` | GitHub App, scheduler, dashboard, notifications, asset gateway | everything |
| `site` | www: catalogue, image pages, explorer, blog | everything except `src/data/` |
| `docs` | docs.linuxserver.io: general guides; image pages are generated | everything except `docs/images/` |
| `stores` | Generated store output per platform | nothing (generated) |
| `proxy-confs` | Generated SWAG samples plus `extra/` for non-LinuxServer apps | `extra/` only |
| `docker-mods` | One branch per mod, `template` branch, `mod.yml` per branch | per branch |
| `docker-<name>` | One container image | see §2 |

Nothing is deployed to any namespace outside `linuxserver-playground`, and images build `FROM` the
playground's own base images and build layers (`ghcr.io/linuxserver-playground/baseimage-*`, `unrar`). An image
is pulled from `ghcr.io/linuxserver/` only where the playground does not publish it or the tag yet. The
workspace's `docs/playground-references.md` lists these rewrites, so they can be swapped back to
`ghcr.io/linuxserver/` when the layout moves to that org.

## 2. Image repository layout

```
Dockerfile              amd64, FROM ghcr.io/linuxserver-playground/baseimage-<base>:<tag>
Dockerfile.aarch64      arm64, identical except the base tag
root/                   copied to / in the image; s6-overlay v3 units under root/etc/s6-overlay/s6-rc.d
image.yml               the manifest (schemas/image.schema.json). The only hand-edited metadata file.
package_versions.txt    the amd64 package table, committed by every successful live release, never hand-edited
README.md               generated by `builder render`, never hand-edited
AGENTS.md               generated by `builder render`, never hand-edited
LICENSE                 GPL-3.0, generated
.github/FUNDING.yml     generated from upstream.sponsor: LinuxServer's sponsor buttons, then the project's donation pages
root/donate.txt         generated from upstream.sponsor, only when it is set; the base images print it at start-up
.github/workflows/build.yml   ~20 lines, generated, calls workflows/image-build.yml@v1
.github/workflows/pr-report.yml   generated, the trusted pull request report
```

`builder render` writes exactly those generated files (and removes `root/donate.txt` when the manifest lists no
sponsor). The docs page and the lite README are rendered
by the hub from the same manifest and never live in an image repository.

There is no Jenkinsfile, no jenkins-vars.yml, no readme-vars.yml, no per-repo trigger workflows, no
issue templates (those come from the org `.github` repo), and no `.jenkins-external`.

Hand-edited: `Dockerfile*`, `root/**`, `image.yml`. Everything else is generated or written by CI.
A pull request that changes a generated file fails `builder check`.

### Branches

Every branch that publishes a tag is a *live branch* and carries its own `image.yml`, whose
`release.branch` names the branch and `release.tag` names the tag it publishes (`latest` for the
default branch, otherwise usually the branch name), as `ls_branch` in `jenkins-vars.yml` did. The shared
workflow, control's fleet discovery and the hub all find live branches that way, from each branch's own
`image.yml`. The default branch's `release.tags` is what the README's Version Tags table and the store
branch pickers advertise: a branch is often cut and released for public testing before it is listed
there, and that is fine. Branches not named in any manifest are *dev branches*: they build and test,
publish to the dev namespace, and never release.

Pull requests build and test fully and publish to the untrusted namespace (§4).

### Kinds

`image.yml` `kind` says what an image is for. Leave it out for an application, the default (`app`). The
`baseimage-*` repos set `kind: base`: images other images build `FROM`. Tools set `kind: tool`: images that are
not a long-running application, run once as a command (ffmpeg, qemu-static) or by the project's own tooling
(build-agent, xvfb), or copied into other images (yq, unrar). An app is what users deploy and leave running,
which is what the stores and install artefacts are for. Base images and tools build, test and release like
any image, but the site lists them on their own tabs, and the hub leaves them out of every store, the
upstream-compatible image list and the install artefacts (Kubernetes, quadlets, SWAG confs). `builder check`
requires `kind: base` exactly on the `baseimage-*` names; `builder migrate` derives both kinds from the name and
the legacy `Internal` category.

## 3. Versions and tags

A release is identified by `<upstream>-ls<N>`:

- `<upstream>` is the upstream version as resolved by `upstream.version` in the manifest, after
  `transform`s, with the characters `~ , % @ + ; : /` and spaces removed.
- `N` is the LinuxServer build number for this branch. It starts at 1 and increments on every release
  of the branch. It is read from the branch's latest GitHub Release tag, never from a registry.
- Images whose `upstream.version.type` is `os` use the first 8 hex characters of the md5 of
  `package_versions.txt` as `<upstream>`, as today.
- `semver` is derived from `<upstream>` when it contains `MAJOR.MINOR.PATCH`; `MAJOR.MINOR` gets the
  build date as patch. It is stored bare; as a tag it takes the same `T-` prefix as every other tag of a
  non-default branch (see the table).

The control plane resolves every live branch's `upstream.version` hourly with the build's own resolver and
dispatches a build when it differs from the branch's newest release, as Jenkins' external triggers did. That
covers every source type but `os` (rebuilt by the weekly package check) and `deb_repo` (it needs docker).
Prefer a typed source to `command`: `github_release` (GitHub's latest release, or the list filtered with
`include`, `exclude`, `prerelease` and `sort`), `deb_packages` and `alpine_apk` (a package index),
`arch_package`, `json` (jq), `regex` (a page or a redirect), `static` (a version pinned by hand), and
`combined` to join two. `command` stays for what none of them can say; the control plane runs it with no
credentials, in an empty directory, and kills it after 120 s.

A source may list what the build downloads under `require_assets`, and the version only counts once all of it
is published: the scheduler records "assets not ready" and tries again next hour instead of dispatching a build
that would fail, holds the branch's release and package checks meanwhile (a held package check keeps its weekly
slot), and a build resolving the version stops with "assets not ready" too. Each entry is a URL
template (`${VERSION}` substituted) that must answer HEAD with 200, or `{asset: <regex>}`, an uploaded asset of
the resolved release whose file name matches (`${VERSION}` is substituted literally; `github_release`,
`codeberg_release` and `gitea_release` only, read by tag as the Dockerfile reads it; with `repo`, the latest
release of that sibling repository instead, for an architecture built from binaries published elsewhere). List one entry per asset
the Dockerfiles fetch, each platform's own, so the record says which one is late. This is what Jenkins'
`external_artifact_check` did in shell. The control plane posts to Discord on every check a branch spends
waiting, amber for the first four and red from the fifth: a release that long without its asset usually means
upstream renamed it, and the pattern and the Dockerfile need updating.

Tag set published on a live release of branch `B` with tag `T` (`T` = `latest` on the default branch):

| Tag | Example (sonarr master) | Example (sonarr develop) |
| --- | --- | --- |
| `T` | `latest` | `develop` |
| `[T-]<upstream>-ls<N>` | `4.0.20.3014-ls1` | `develop-5.0.1.1234-ls7` |
| `[T-]version-<upstream>` | `version-4.0.20.3014` | `develop-version-5.0.1.1234` |
| `[T-]<semver>` when derivable | `4.0.20` | `develop-5.0.1` |
| `<arch>-` prefixed twins of all of the above | `amd64-latest`, `arm64v8-4.0.20.3014-ls1` | |

Architecture prefixes are `amd64-` and `arm64v8-`. The unprefixed tags are multi-platform indexes.

The git tag and GitHub Release are named `[T-]<upstream>-ls<N>` and are created only on live releases. The
Release's `target_commitish` is always the branch name, never a sha, so a branch's releases can be listed
without parsing tag prefixes.

### Mods

A mod branch `<target>-<name>` publishes `ghcr.io/linuxserver-playground/mods:<target>-<name>` and
`:<target>-<name>-<sha7>`; mods have no GitHub Releases and no build number. A mod that packages one upstream
tool says so in `mod.yml` `upstream` (`url`, and `version`: any `upstream.version` source type above except `os`,
`command` and `deb_repo`, `combined` included). Then:

- the build resolves it with the same resolver unless it is given a `mod_version`, passes it as the
  `MOD_VERSION` build arg (the Dockerfile declares `ARG MOD_VERSION`; its own lookup is only the fallback for
  local builds) and the `org.opencontainers.image.version` label, and also tags `:<target>-<name>-<version>` and
  `:<target>-<name>-<version>-<sha7>`, `<version>` being the version with the characters listed above removed;
- the control plane checks it hourly, spread over the hour like the images, and dispatches the branch's
  `build.yml` with that `mod_version` when `:<target>-<name>-<version>` does not exist yet. That tag is the
  record of what was built, as Docker Hub's was for the Jenkins triggers.

`combined` joins several sources, each resolved with its own `transform`, with `separator` (`-` by default),
for a version made of two upstreams (docker and compose); the outer `transform` then applies to the result.

`upstream.version` is the mod's default line, the one `:<target>-<name>` follows. When upstream ships several
version lines at once (Go's two supported releases and its release candidate), `upstream.lines` lists the others,
each with a `name` and its own `version` source, in order of priority. Each line is checked on its own: control
dispatches `build.yml` with `mod_version` and `line` (an input only a branch with lines has, rendered by
`builder render-mod`), at most one build of a branch at a time, and the build of a line tags
`:<target>-<name>-<version>` and its `-<sha7>` twin but never `:<target>-<name>` or `:<target>-<name>-<sha7>`.
`tags` (on the default line or any other) also moves floating tags with every build of that line: `major` is
`:<target>-<name>-X` and `minor` `:<target>-<name>-X.Y` of a version `X.Y.Z` (the version up to its first or
second dot; a version without that dot gets no such tag). When two lines resolve to the same version, the
earlier line builds it.

## 4. Namespaces

| Mode | When | Image | Tags | Lifetime |
| --- | --- | --- | --- | --- |
| live | push to a live branch, or scheduler dispatch | `ghcr.io/linuxserver-playground/<name>` | §3 | permanent |
| dev | push to any other branch | `ghcr.io/linuxserver-playground/dev/<name>` | `<branch>-<sha7>`, arch twins | 30 days |
| pr | pull_request | `ghcr.io/linuxserver-playground/untrusted-pr/<name>` | `pr-<number>-<sha7>`, arch twins | deleted when the PR closes |

Images in `dev/` and `untrusted-pr/` carry
`org.opencontainers.image.description=UNREVIEWED <mode> build of <name>. Not for production use.` and
never receive a `latest` tag. Pull requests from forks run without secrets: they build and test, and the
image is uploaded as a workflow artifact instead of being pushed.

## 6. The build bundle

A live release attaches these assets to its GitHub Release. Names are fixed; `<arch>` is `amd64` or
`arm64`.

| Asset | Schema | Notes |
| --- | --- | --- |
| `build.json` | `schemas/bundle.schema.json` | The record. Everything the hub needs that is small. |
| `packages.<arch>.json.gz` | syft JSON | Packages only: `SYFT_FILE_METADATA_SELECTION=none`, `+sbom-cataloger`, trimmed of file records, per-package file lists and file relationships |
| `layers.<arch>.json` | in `bundle.schema.json` `$defs/layer` (array) | From the manifest, `docker history` and provenance |
| `files.<arch>.json.gz` | in `bundle.schema.json` `$defs/file_tree` | `dumper files` inside the image: a nested tree with sizes, link targets, permissions and owners; hardlinks exact from inodes |
| `test.<arch>.json` | `schemas/test-report.schema.json` | One per arch |
| `test.<arch>.tar.gz` | | Screenshot, container and browser logs, sysinfo, package diff, shellcheck XML |
| `package_versions.<arch>.txt` | text | syft table, the human-readable list |
| `record.json` | `schemas/record.schema.json` | Everything the hub stores about the build, derived in the publish job by `builder record`: the normalised package tables, the diff against the previous release of the branch (with the repository commits between the two, who made them and what they touched, from GitHub's compare), the grype scan of both architectures, the layers, the test reports and the base image's layer digests. The hub ingests a release from `build.json` and this file alone; a part the build could not derive is listed in `errors` and the hub derives it instead. |

After a live release's run has completed successfully, the control plane attaches two more assets (the
run's own last steps are in them, so the workflow cannot). They appear a minute or more after the Release.

| Asset | Notes |
| --- | --- |
| `run.json` | The run's record, `schema` 1, in GitHub's field names: `archived_at`, `repository`, `release` {`tag`, `url`}, `build` {`image`, `branch`, `mode`, `version_tag`, `release_tag`}, `run` {`id`, `name`, `path`, `run_number`, `run_attempt`, `html_url`, `display_title`, `event`, `status`, `conclusion`, `created_at`, `run_started_at`, `updated_at`}, `trigger` {`event`, `reason`, `actor`, `triggering_actor`}, `head` {`branch`, `sha`, `message`, `timestamp`, author `name`}, `jobs[]` {`id`, `name`, `html_url`, `run_attempt`, `status`, `conclusion`, `created_at`, `started_at`, `completed_at`, `runner_name`, `runner_group_name`, `labels`, `steps[]` {`number`, `name`, `status`, `conclusion`, `started_at`, `completed_at`}}. `trigger.reason` is the build's own `reason`: the REST API exposes no dispatch inputs |
| `logs.zip` | The run's log archive as GitHub serves it, secrets masked. Uploaded only when a check for credential-shaped strings finds none, so a Release may have `run.json` without it; GitHub keeps logs 90 days, so an older run gets `run.json` only |

The image itself carries the same packages-only SBOM as SPDX 2.3 (`sbom.<arch>.spdx.json` from the ci run),
attached by the publish job in BuildKit's attestation layout next to the provenance, so
`docker buildx imagetools inspect --format '{{json .SBOM}}'` and Docker tooling read it. BuildKit's own
`--sbom` scan is off: it records every file and outgrew the 80 MiB attestation limit on desktop images.

`build.json` `published` is what the publish job pushed, as publish-manifest reports it: the image (`image`)
and every tag it created (`tags`), the unprefixed ones then their arch-prefixed twins. Readers of a build's tags
take them from there (and, for a release from before contracts 1.10, from `version.tags`, which its publish pushed
in full), never from a registry listing: a build's tags are fixed when it publishes, and only the floating ones
move on to the branch's next build.

Data about one build is made by the build: the publish job has the image's SBOMs, test results and the
previous release in hand, so it computes what the hub and the website show for the build, and the hub only
indexes it. The derivation code (`builder.derive`) is the one the hub uses for releases made before
`record.json` existed. The vulnerability scan in `record.json` is the state of the image as it was released,
scanned with that day's database. Nothing rescans it: it is informal, best-effort data shown on the build's page,
not a security feed.

`build.json` is also written to the workflow job summary and sent to the control plane as a
`build.summary` event (`schemas/control-event.schema.json`), after the live release's Pages deploy (below), whose
outcome the event's `pages` carries. PR and dev builds produce the same bundle
as workflow artifacts (not Release assets) so reviewers get the same data. A PR build's report (tests per
arch, screenshots, runtime, package changes, log tails) is its pull request comment; a dev or live build's job
summary opens with the same report, and that run page is where notifications link a build without a page on
the website.

### Repo Pages

Every image repository has GitHub Pages, deployed from GitHub Actions (the `github-pages` environment allows
every branch). Its site is the browser-readable home of the heavy files of the repository's newest live
builds, so the hub does not copy them. Pages answers with `access-control-allow-origin: *`: any website
can fetch them. `PAGES` is `https://<owner>.github.io/<repo>`, derived from the repository, never written
down.

Nothing is committed for it. The shared workflow assembles the site from the repository's GitHub Releases
into an empty directory and deploys it as a workflow artifact: in the publish job of every live release, right
after the Release and before the `build.summary` event (§10), and on its own when the build runs with
`reason: pages` (filling or repairing a site). Each deploy
is complete by itself, so a lost one is repaired by the next. The Releases stay the archive of everything.

Each build's folder also carries copies of its per-build documents as the hub's API serves them, without the API's
envelope: `build.json` (the Release asset as it is), `report.json`, `tests.json`, `diff.json`, `layers.<arch>.json`
and `packages.<arch>.json`. One implementation shapes them for both, `builder.derive.documents` (with
`builder.derive.layers`): the hub renders its routes with it, and the pages assembler writes these copies with it,
from `record.json` or, for a release without one, from the other assets with the code `builder record` runs. The
hub is the API for them (§10): nothing may depend on these copies. In them every link (`links`) points at the
repository's Pages, and `report.json` has no `is_newest`, which changes after the release.

| Path | What |
| --- | --- |
| `PAGES/index.json` | `{"schema": "lsio-pages/1", "repo": "<owner>/<repo>", "generated_at": "<ISO 8601>", "keep": 5, "builds": [...]}`, each build `{"tag", "branch", "published_at", "arches": [...]}`, newest first |
| `PAGES/builds/<tag>/files.<arch>.json.gz` | The Release asset as it is. Pages serves it as `application/gzip` without `Content-Encoding`: readers gunzip it themselves |
| `PAGES/builds/<tag>/packages.<arch>.json.gz` | The Release asset as it is |
| `PAGES/builds/<tag>/vulns.json` | The build's own scan from `record.json` `vulns`, shaped by `builder.derive.vulns.document`: `{"image", "tag", "summary", "by_arch", "matches", "db_date", "grype_version", "scanned_at", "caveats"}`. `summary` and each `by_arch` entry count `critical`, `high`, `medium`, `low`, `negligible`, `unknown`, `fixed`, `unfixed` and `wont_fix` over the merged rows; `matches` holds one row per vulnerability id and package across the architectures, worst first, each record.json's row plus the `arches` it was found on; `scanned_at` is the earliest scan (absent when the record has no time). Absent when the record has no scan. It is never rescanned |
| `PAGES/builds/<tag>/<arch>/…` | `test.<arch>.tar.gz` unpacked as the hub's build reports unpack it: the files `test.<arch>.json` names under fixed names (`screenshot.png`, `container.log`, `browser.log`, `sysinfo.txt`, `shellcheck.xml`), `package_diff.txt`, everything else under its path in the archive with one leading directory stripped. Never the harness's retired `index.html`; at most 64 MiB per tarball |

The site keeps the newest 5 releases (by `published_at`) of each live branch, and only live releases. A
branch is live when its own `image.yml` names it in `release.branch`. A release belongs to the branch its
`target_commitish` names (§3); one whose `target_commitish` is a commit sha belongs to the live branch whose
release tag prefixes its tag (the longest such tag), else to the default branch; one made from a branch that
is no longer live is left out. Should a site outgrow 900 MiB (Pages refuses 1 GB), the oldest builds that
are not their branch's newest are left out, with a warning. A build that is not in `index.json` links to its
Release.

## 7. Release notes

The Release body has three sections, in order: **CI**, a link to the build's CI results page on the website
(§10); **LinuxServer changes**, GitHub's auto-generated notes for the commits since the previous release of the
branch; **Upstream changes**, the text fetched by `upstream.notes`, verbatim, with its source URL. The
hub stores all three.

`upstream.notes` names where the text comes from: `github_release`, `codeberg_release` and `gitea_release` (the
release body, looked up by `tag`, a template over `${VERSION}`), `github_commit` and `gitlab_commit` (the commit
message of the version), `json` (the whole output of a jq expression), `rss` (the feed item titled after the
version), `command`, or `none`. The version is the one the build resolved, packaging suffix and all; a notes
block whose source spells it differently lists `transform` substitutions, applied before `${VERSION}` is
substituted anywhere in the block (`-r\d+$` to `` for an Alpine package, `-\d+$` for an Arch one). A fetch that
finds nothing leaves the section empty rather than failing the release.

## 8. Commits, pull requests, agents

- Commit subjects are short imperative sentences: `Add krb5-libs for postgresql support`. No
  conventional-commit prefixes, no emoji, no trailers of any kind.
- Bot commits on live branches are limited to: `Update generated files [skip ci]` (README, AGENTS.md, workflow
  after a manifest change, made before the build, which continues on it) and `Update package versions [skip ci]`
  (the amd64 package table, made after a successful release, so the committed table never lags the released
  image). Both are made by the shared workflow, once, and neither starts a build: the control plane's release
  check treats a head that differs from the released commit only in these files as released.
- Every repo has an `AGENTS.md`. Image repos and mods get it generated from `templates/agents/`; the
  infrastructure repos write their own but keep the same headings: Purpose, Layout, What you may edit,
  How to validate locally, Pull request rules.
- A PR that touched generated files, or whose manifest does not validate, fails `builder check` with the
  file, field and line.
- AI-assisted contributions are welcome and must be disclosed in the PR description.

## 9. Secrets and tokens

- The shared workflow needs no long-lived secrets for live builds: `GITHUB_TOKEN` with
  `packages: write`, `contents: write` is enough to push to GHCR and create Releases in the same org, and
  `pages: write` with `id-token: write` to deploy the repository's Pages site (§6).
- The hub ingests through `repository_dispatch`, sent with the GitHub App installation token held by the
  control plane, or on its own hourly reconciliation. Image repos never hold a hub token.
- Discord and any other notification sinks are configured only in the control plane.
- Nothing in any repo may contain a credential. `builder check` greps for the usual shapes.

## 10. Events to the control plane

The control plane learns most things from GitHub webhooks (`workflow_run`, `workflow_job`,
`pull_request`, `release`, `issues`). The shared workflow additionally POSTs one `build.summary` event
at the end of every run, authenticated with an HMAC over the body using a per-org secret
(`CONTROL_EVENTS_SECRET`), because GitHub's events do not carry the image, tag and test results.
Shape: `schemas/control-event.schema.json`.

A live release sends it after its Pages deploy, so that when the control plane hears of a release the build's
files are on its repository's Pages (the screenshot, report files, file trees and `vulns.json` its page on the
website reads), or the event says they are not: `pages` is `deployed` (the site went out with this release),
`failed` (every deploy attempt failed; the site serves its previous deploy, without this release, until the next
release or a `reason: pages` run repairs it) or `skipped` (no release, no deploy attempted). The Pages step never
fails the run, so this field is the only place its failure shows. A `reason: pages` run sends no event; its one job
fails when no deploy succeeded.

### Who renders what

The control plane runs on modest hardware and is public. It shows live build status, the fleet board,
queue, scheduler decisions and maintainer actions, and nothing else. Everything derived from a release
(test reports, screenshots, logs, package and file data, diffs, store templates, docs) is static: the hub
renders its data and generated artefacts on GitHub Pages from the Release assets, each image repository's Pages
holds the heavy files of its builds, and the website renders the pages people read from both. Links in release notes, Discord messages
and READMEs point at the website for results and at the control plane only for live run status; the website
renders the fleet dashboard from the control plane's API.

| Route | Owner | Purpose |
| --- | --- | --- |
| `{SITE_URL}/images/{image}/builds/{tag}/` | site | The CI results page of one live build, rendered from the hub's data: per-arch test table, screenshot, logs, diff, explorer. It exists as soon as the hub serves the build: until the site's next build makes it a static page, the site's 404 page renders it in the browser from the hub's API. `test.report_url` in the bundle, the CI section of release notes and Discord embeds point here. Section anchors are stable (`#quick-start`, `#setup`, `#parameters`, `#proxy`, `#mods`, `#builds`, `#fleet`). |
| `{HUB_URL}/builds/{image}/{tag}/` | hub | A redirect to `{SITE_URL}/images/{image}/builds/{tag}/`, for every build the hub knows, retained or in its history: older release notes and bundles linked the hub's retired report pages. |
| `{PAGES}/index.json`, `{PAGES}/builds/{tag}/...` | image repo (shared workflow) | The heavy files of the newest 5 live builds of each branch, readable cross-origin, the build's as-released vulnerability scan (`vulns.json`) among them (§6, "Repo Pages"). |
| `{SITE_URL}/fleet/...` | site | The fleet dashboard, rendered from the control plane's JSON API with cookie sign-in. |
| `{HUB_URL}/builds/{image}/` | hub | A redirect to the image page's build list, `{SITE_URL}/images/{image}/#builds`. |
| `{HUB_URL}/stores/...`, `{HUB_URL}/api/v1/...` | hub | Store templates and the static API. |
| `{CONTROL_URL}/builds/{owner}/{repo}/{run_id}` | control | Live status of one run: jobs, timings, result, links to the site's build page once published. |

`SITE_URL`, `HUB_URL` and `CONTROL_URL` are org-level Actions variables; the shared workflow reads them.

## 11. Versioning the contracts

`contracts_version` in `pyproject.toml` is `MAJOR.MINOR`. A MINOR change adds optional fields; a MAJOR
change renames or removes. Every schema has a top-level `schema` integer that equals the MAJOR. Producers
write it; consumers refuse what they do not understand and say so.
