# LinuxServer v2 conventions

This file is the contract every repository in the `linuxserver-playground` organisation is built
against. The JSON Schemas in `schemas/` are the machine-checkable half; this document is the half that
explains intent. When a repo's own docs and this file disagree, this file wins. Change it by pull
request to this repo, and bump `contracts_version` in `pyproject.toml` when a schema changes shape.

The blueprint behind these conventions is the "LinuxServer v2 Blueprint" page. The short version:
image repos are thin and described by one manifest; one shared GitHub Actions workflow builds every
image; each build attaches a bundle to its GitHub Release; the hub ingests bundles and generates every
downstream artefact; a public control plane schedules builds and shows the whole fleet.

## 1. Repositories

| Repo | Owns | Hand-edited files |
| --- | --- | --- |
| `builder` | Contracts (this file, `schemas/`), the manifest validator and renderer, AGENTS.md templates | everything |
| `workflows` | Reusable GitHub Actions workflows and composite actions, tagged `v1` | everything |
| `ci` | The container test harness and bundle emitters | everything |
| `hub` | Ingest, data, static API, generators (docs pages, stores, proxy confs, kubernetes, mods index) | everything except `data/` |
| `control` | GitHub App, scheduler, dashboard, notifications, asset gateway | everything |
| `site` | www: catalogue, image pages, explorer, blog | everything except `src/data/` |
| `docs` | docs.linuxserver.io: general guides; image pages are generated | everything except `docs/images/` |
| `stores` | Generated store output per platform | nothing (generated) |
| `proxy-confs` | Generated SWAG samples plus `extra/` for non-LinuxServer apps | `extra/` only |
| `docker-mods` | One branch per mod, `template` branch, `mod.yml` per branch | per branch |
| `docker-<name>` | One container image | see §2 |

Nothing is deployed to any namespace outside `linuxserver-playground`. Base images are pulled read-only
from `ghcr.io/linuxserver/baseimage-*` until a base image repo joins the playground.

## 2. Image repository layout

```
Dockerfile              amd64, FROM ghcr.io/linuxserver/baseimage-<base>:<tag>
Dockerfile.aarch64      arm64, identical except the base tag
root/                   copied to / in the image; s6-overlay v3 units under root/etc/s6-overlay/s6-rc.d
image.yml               the manifest (schemas/image.schema.json). The only hand-edited metadata file.
package_versions.txt    written by the build, committed on the live branch, never hand-edited
README.md               generated by `builder render`, never hand-edited
AGENTS.md               generated by `builder render`, never hand-edited
LICENSE                 GPL-3.0, generated
.github/workflows/build.yml   ~20 lines, generated, calls workflows/image-build.yml@v1
```

`builder render` writes exactly those four generated files. The docs page and the lite README are rendered
by the hub from the same manifest and never live in an image repository.

There is no Jenkinsfile, no jenkins-vars.yml, no readme-vars.yml, no per-repo trigger workflows, no
issue templates (those come from the org `.github` repo), and no `.jenkins-external`.

Hand-edited: `Dockerfile*`, `root/**`, `image.yml`. Everything else is generated or written by CI.
A pull request that changes a generated file fails `builder check`.

### Branches

Every branch that publishes a tag is a *live branch* and carries its own `image.yml`, whose
`release.branch` names the branch and `release.tag` names the tag it publishes (`latest` for the
default branch, otherwise usually the branch name). The default branch's `release.tags` lists every
live branch's tag, its own included: control and the hub find live branches through that list, so a
release from an unlisted branch gets no website page and no scheduled checks, and the shared workflow
refuses to release it. Branches not named in any manifest are *dev branches*: they build and test,
publish to the dev namespace, and never release.

Pull requests build and test fully and publish to the untrusted namespace (§4).

### Kinds

`image.yml` `kind` says what an image is for. Leave it out for an application, the default (`app`). The
`baseimage-*` repos set `kind: base`: images other images build `FROM`. Internal tools that the project's own
tooling runs (xvfb, yq, build-agent) set `kind: tool`. Base images and tools build, test and release like
any image, but the site lists them on their own tabs, and the hub leaves them out of every store, the
upstream-compatible image list and the install artefacts (Kubernetes, quadlets, SWAG confs). `builder check`
requires `kind: base` exactly on the `baseimage-*` names; `builder migrate` derives both kinds from the name and
the legacy `Internal` category.

## 3. Versions and tags

A release is identified by `<upstream>-ls<N>`:

- `<upstream>` is the upstream version as resolved by `upstream.version` in the manifest, after
  `transform`s, with the characters `~ , % @ + ; : /` and spaces removed.
- `N` is the LinuxServer build number for this branch. It starts at 1 and increments on every release
  of the branch. It is read from the branch's latest GitHub Release tag, never from a registry.
- Images whose `upstream.version.type` is `os` use the first 8 hex characters of the md5 of
  `package_versions.txt` as `<upstream>`, as today.
- `semver` is derived from `<upstream>` when it contains `MAJOR.MINOR.PATCH`; `MAJOR.MINOR` gets the
  build date as patch. It is stored bare; as a tag it takes the same `T-` prefix as every other tag of a
  non-default branch (see the table).

Tag set published on a live release of branch `B` with tag `T` (`T` = `latest` on the default branch):

| Tag | Example (sonarr master) | Example (sonarr develop) |
| --- | --- | --- |
| `T` | `latest` | `develop` |
| `[T-]<upstream>-ls<N>` | `4.0.20.3014-ls1` | `develop-5.0.1.1234-ls7` |
| `[T-]version-<upstream>` | `version-4.0.20.3014` | `develop-version-5.0.1.1234` |
| `[T-]<semver>` when derivable | `4.0.20` | `develop-5.0.1` |
| `<arch>-` prefixed twins of all of the above | `amd64-latest`, `arm64v8-4.0.20.3014-ls1` | |

Architecture prefixes are `amd64-` and `arm64v8-`. The unprefixed tags are multi-platform indexes.

The git tag and GitHub Release are named `[T-]<upstream>-ls<N>` and are created only on live releases. The
Release's `target_commitish` is always the branch name, never a sha, so a branch's releases can be listed
without parsing tag prefixes.

## 4. Namespaces

| Mode | When | Image | Tags | Lifetime |
| --- | --- | --- | --- | --- |
| live | push to a live branch, or scheduler dispatch | `ghcr.io/linuxserver-playground/<name>` | §3 | permanent |
| dev | push to any other branch | `ghcr.io/linuxserver-playground/dev/<name>` | `<branch>-<sha7>`, arch twins | 30 days |
| pr | pull_request | `ghcr.io/linuxserver-playground/untrusted-pr/<name>` | `pr-<number>-<sha7>`, arch twins | deleted when the PR closes |

Images in `dev/` and `untrusted-pr/` carry
`org.opencontainers.image.description=UNREVIEWED <mode> build of <name>. Not for production use.` and
never receive a `latest` tag. Pull requests from forks run without secrets: they build and test, and the
image is uploaded as a workflow artifact instead of being pushed.

## 5. Labels

Every image carries these OCI labels, set by the shared workflow:

```
org.opencontainers.image.created        build time, RFC 3339
org.opencontainers.image.authors        linuxserver.io
org.opencontainers.image.url            https://github.com/linuxserver-playground/docker-<name>/packages
org.opencontainers.image.documentation  https://docs.linuxserver.io/images/docker-<name>
org.opencontainers.image.source         https://github.com/linuxserver-playground/docker-<name>
org.opencontainers.image.version        <upstream>-ls<N>  (dev/pr: the dev or pr tag)
org.opencontainers.image.revision       git sha
org.opencontainers.image.vendor         linuxserver.io
org.opencontainers.image.licenses       GPL-3.0-only
org.opencontainers.image.title          <title>
org.opencontainers.image.description    <summary, first sentence> (dev/pr: the warning in §4)
io.linuxserver.image.mode               live | dev | pr
io.linuxserver.image.branch             git branch
io.linuxserver.image.upstream           <upstream> before sanitising
io.linuxserver.image.base               base image reference with digest
build_version                           "Linuxserver.io version:- <version> Build-date:- <date>"  (kept for compatibility)
```

`ENV LSIO_FIRST_PARTY=true` is injected after `FROM` for non-base images, as today.

## 6. The build bundle

A live release attaches these assets to its GitHub Release. Names are fixed; `<arch>` is `amd64` or
`arm64`.

| Asset | Schema | Notes |
| --- | --- | --- |
| `build.json` | `schemas/bundle.schema.json` | The record. Everything the hub needs that is small. |
| `packages.<arch>.json.gz` | syft JSON | Packages only: `SYFT_FILE_METADATA_SELECTION=none`, `+sbom-cataloger`, trimmed of file records, per-package file lists and file relationships |
| `layers.<arch>.json` | in `bundle.schema.json` `$defs/layer` (array) | From the manifest, `docker history` and provenance |
| `files.<arch>.json.gz` | in `bundle.schema.json` `$defs/file_tree` | `dumper files` inside the image: a nested tree with sizes, link targets, permissions and owners; hardlinks exact from inodes |
| `test.<arch>.json` | `schemas/test-report.schema.json` | One per arch |
| `test.<arch>.tar.gz` | | Screenshot, container and browser logs, sysinfo, package diff, shellcheck XML |
| `package_versions.<arch>.txt` | text | syft table, the human-readable list |
| `record.json` | `schemas/record.schema.json` | Everything the hub stores about the build, derived in the publish job by `builder record`: the normalised package tables, the diff against the previous release of the branch, the grype scan of both architectures, the layers, the test reports and the base image's layer digests. The hub ingests a release from `build.json` and this file alone; a part the build could not derive is listed in `errors` and the hub derives it instead. |

The image itself carries the same packages-only SBOM as SPDX 2.3 (`sbom.<arch>.spdx.json` from the ci run),
attached by the publish job in BuildKit's attestation layout next to the provenance, so
`docker buildx imagetools inspect --format '{{json .SBOM}}'` and Docker tooling read it. BuildKit's own
`--sbom` scan is off: it records every file and outgrew the 80 MiB attestation limit on desktop images.

Data about one build is made by the build: the publish job has the image's SBOMs, test results and the
previous release in hand, so it computes what the hub and the website show for the build, and the hub only
indexes it. The derivation code (`builder.derive`) is the one the hub uses for releases made before
`record.json` existed. The vulnerability scan is also repeated by the hub on the database's clock, so the
newest build of every branch keeps current findings.

`build.json` is also written to the workflow job summary and sent to the control plane as a
`build.summary` event (`schemas/control-event.schema.json`). PR and dev builds produce the same bundle
as workflow artifacts (not Release assets) so reviewers get the same data. A PR build's report (tests per
arch, screenshots, runtime, package changes, log tails) is its pull request comment; a dev or live build's job
summary opens with the same report, and that run page is where notifications link a build without a page on
the website.

## 7. Release notes

The Release body has three sections, in order: **CI**, a link to the build's CI results page on the website
(§10); **LinuxServer changes**, GitHub's auto-generated notes for the commits since the previous release of the
branch; **Upstream changes**, the text fetched by `upstream.notes`, verbatim, with its source URL. The
hub stores all three.

## 8. Commits, pull requests, agents

- Commit subjects are short imperative sentences: `Add krb5-libs for postgresql support`. No
  conventional-commit prefixes, no emoji, no trailers of any kind.
- Bot commits on live branches are limited to: `Update generated files` (README, AGENTS.md, workflow
  after a manifest change) and `Update package versions`. Both are made by the shared workflow, once,
  and do not restart the build.
- Every repo has an `AGENTS.md`. Image repos and mods get it generated from `templates/agents/`; the
  infrastructure repos write their own but keep the same headings: Purpose, Layout, What you may edit,
  How to validate locally, Pull request rules.
- A PR that touched generated files, or whose manifest does not validate, fails `builder check` with the
  file, field and line.
- AI-assisted contributions are welcome and must be disclosed in the PR description.

## 9. Secrets and tokens

- The shared workflow needs no long-lived secrets for live builds: `GITHUB_TOKEN` with
  `packages: write`, `contents: write` is enough to push to GHCR and create Releases in the same org.
- The hub ingests through `repository_dispatch`, sent with the GitHub App installation token held by the
  control plane, or on its own hourly reconciliation. Image repos never hold a hub token.
- Discord and any other notification sinks are configured only in the control plane.
- Nothing in any repo may contain a credential. `builder check` greps for the usual shapes.

## 10. Events to the control plane

The control plane learns most things from GitHub webhooks (`workflow_run`, `workflow_job`,
`pull_request`, `release`, `issues`). The shared workflow additionally POSTs one `build.summary` event
at the end of every run, authenticated with an HMAC over the body using a per-org secret
(`CONTROL_EVENTS_SECRET`), because GitHub's events do not carry the image, tag and test results.
Shape: `schemas/control-event.schema.json`.

### Who renders what

The control plane runs on modest hardware and is public. It shows live build status, the fleet board,
queue, scheduler decisions and maintainer actions, and nothing else. Everything derived from a release
(test reports, screenshots, logs, package and file data, diffs, store templates, docs) is rendered by the
hub into static files on GitHub Pages, from the Release assets. Links in release notes, Discord messages
and READMEs point at the website for results and at the control plane only for live run status; the website
renders the fleet dashboard from the control plane's API.

| Route | Owner | Purpose |
| --- | --- | --- |
| `{SITE_URL}/images/{image}/builds/{tag}/` | site | The CI results page of one live build, rendered from the hub's data: per-arch test table, screenshot, logs, diff, explorer. It exists as soon as the hub serves the build: until the site's next build makes it a static page, the site's 404 page renders it in the browser from the hub's API. `test.report_url` in the bundle, the CI section of release notes and Discord embeds point here. Section anchors are stable (`#quick-start`, `#setup`, `#parameters`, `#proxy`, `#mods`, `#builds`, `#fleet`). |
| `{HUB_URL}/builds/{image}/{tag}/` | hub | The same results as plain static pages and the unpacked report files the site reads. |
| `{SITE_URL}/fleet/...` | site | The fleet dashboard, rendered from the control plane's JSON API with cookie sign-in. |
| `{HUB_URL}/builds/{image}/` | hub | Build history of one image. |
| `{HUB_URL}/stores/...`, `{HUB_URL}/api/v1/...` | hub | Store templates and the static API. |
| `{CONTROL_URL}/builds/{owner}/{repo}/{run_id}` | control | Live status of one run: jobs, timings, result, links to the hub page once published. |
| `{CONTROL_URL}/images/{name}` and `/images/{name}/{tag}` | control | Fleet-board drill-down; README badges link here. |
| `{CONTROL_URL}/badge/{name}/{tag}.svg` | control | CI status badge for the latest live build with that release tag. |
| `{CONTROL_URL}/events` | control | Signed `build.started` / `build.summary` intake (above). |

`SITE_URL`, `HUB_URL` and `CONTROL_URL` are org-level Actions variables; the shared workflow reads them.

## 11. Versioning the contracts

`contracts_version` in `pyproject.toml` is `MAJOR.MINOR`. A MINOR change adds optional fields; a MAJOR
change renames or removes. Every schema has a top-level `schema` integer that equals the MAJOR. Producers
write it; consumers refuse what they do not understand and say so.
